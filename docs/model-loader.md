# Advanced model loader

The model-loader lesson answers a practical Dreamcast question: how should a
modern authoring asset become something the SH-4 and PVR can submit safely?
It loads a small textured satellite model through a purpose-built DCM1 binary
blob and expands it into the existing TexturedMesh API.

Build and run the lesson with:

~~~sh
python3 tools/obj-to-dcmodel.py \
  advanced_examples/assets/satellite.obj \
  advanced_examples/assets/model_asset.hpp
make dreamcast-model-loader-cdi
make flycast-model-loader
~~~

The first command is an offline asset step. The Dreamcast ELF contains the
generated byte array, so the runtime does not need a filesystem, an OBJ parser,
or a JSON parser.

## What the Dreamcast can render

The PVR does not receive a general-purpose model object. KallistiOS's public
generic vertex packet carries screen-space x, y, z, texture u, v, packed vertex
color, and offset color; see the
[KallistiOS pvr_vertex_t documentation](https://kos-docs.dreamcast.wiki/structpvr__vertex__t.html).
The project therefore performs model/view/projection, clipping, and conversion
to PVR vertices on the SH-4 before calling the existing list submission path.
There is no target-side vertex shader, scene graph, skeletal-animation system,
or material parser hidden in this example.

The public KOS PVR header also notes that the bins and vertex buffers come from
the texture-memory pool. The KOS implementation describes the vertex buffer,
object pointer buffers, and tile matrix as separate parts of the
tile-accelerator pipeline in its
[PVR internals](https://github.com/KallistiOS/KallistiOS/blob/master/kernel/arch/dreamcast/hardware/pvr/pvr_internal.h).
That is why “maximum triangles” is not one useful universal number: the cost
depends on submitted vertices, visible tile coverage, list state, textures,
depth/opacity choices, and the configured PVR buffers.

For this repository's pinned baseline, the PVR vertex buffer is configured to
512 KiB and the public texture path uses 16-bit ARGB4444 texels. Those are
project configuration and lesson boundaries, not measurements of total
Dreamcast throughput. A larger model must be measured on the target or a
known emulator configuration rather than inferred from the small fixture.

## Why not parse glTF on the console?

[glTF 2.0](https://github.com/KhronosGroup/glTF/blob/main/specification/2.0/Specification.adoc)
is a useful interchange and runtime-delivery format: it combines a JSON scene
description with binary geometry, animation, and image resources. Its complete
scene model is much richer than this lesson needs. Parsing that structure on a
Dreamcast would add a JSON reader, scene/material handling, resource lifetime
rules, and often texture conversion work to the target executable.

The lesson instead treats OBJ or glTF as authoring/publishing input and makes a
small, explicit conversion step. This preserves the useful workflow while
keeping target costs visible:

* author or export a triangulated low-poly model;
* validate its dimensions and UV range offline;
* duplicate position/UV pairs at texture seams;
* quantize positions and UVs to the representation the lesson can decode;
* upload a separately converted PVR texture;
* submit the decoded vertices through the existing PVR list boundary.

This is not a claim that glTF is unsuitable for every Dreamcast game. It is a
deliberate choice for a first loader lesson where a compact target format is
more instructive than a full scene-format implementation.

## DCM1 format

DCM1 is the private, versioned format used by this example. All integers are
little-endian. The header is 24 bytes:

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII magic DCM1 |
| 4 | 2 | Format version, currently 1 |
| 6 | 2 | Flags, currently 1 for textured vertices |
| 8 | 2 | Vertex count |
| 10 | 2 | Index count; must be a multiple of three |
| 12 | 4 | Vertex-record offset; currently 24 |
| 16 | 4 | Index-array offset |
| 20 | 4 | Total file size |

Each vertex record is 16 bytes:

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 2 | Signed X in Q8.8 fixed point |
| 2 | 2 | Signed Y in Q8.8 fixed point |
| 4 | 2 | Signed Z in Q8.8 fixed point |
| 6 | 2 | U in Q0.16 normalized texture coordinates |
| 8 | 2 | V in Q0.16 normalized texture coordinates |
| 10 | 4 | Packed ARGB color |
| 14 | 2 | Reserved, currently zero |

Indices are unsigned 16-bit references into the decoded vertex array. The
loader rejects bad magic, version, flags, offsets, file size, count limits, and
out-of-range indices before submitting anything. It expands fixed-point data
into the existing maishuji::TexturedMeshVertex representation using fixed
arrays sized for this lesson; it does not allocate from the heap.

The checked-in sample is:

| Item | Value |
| --- | ---: |
| DCM1 blob | 1,336 bytes |
| Decoded vertices | 67 |
| Triangle indices | 120 |
| Triangles | 40 |
| Texture | 32x32 ARGB4444, 2,048 bytes |

The generated header is an embedding representation. The readable source of
the model is
[advanced_examples/assets/satellite.obj](../advanced_examples/assets/satellite.obj),
and the conversion tool is
[tools/obj-to-dcmodel.py](../tools/obj-to-dcmodel.py).

## The supported OBJ subset

The converter accepts v, vt, and f records and ignores object, group,
smoothing, and material labels. Faces may use v/vt or v/vt/vn corners; polygons
are triangulated as a fan. Negative OBJ indices are accepted. Every corner must
have a UV, UVs must be in the inclusive 0..1 range, and positions must fit
signed Q8.8.

The converter keys output vertices by (position index, UV index). This is
important: one geometric position may need multiple output vertices when a
texture seam gives each face a different UV. The output is therefore not
trying to minimize vertex count at all costs; it preserves the attributes the
PVR vertex packet needs.

Unsupported on purpose:

* normals and normal maps;
* multiple materials or per-face render-list choices;
* animations, skinning, morph targets, and node hierarchies;
* indexed formats wider than 16 bits;
* texture conversion or PVR compression.

Those features can be added as separate lessons once the asset and memory
budgets are explicit. They should not be implied by a loader that only
supports one static textured mesh.

## Submission cost

At the fixed sample pose, the existing mesh path has one polygon header and
three vertex packets per submitted model triangle:

| Workload | Headers | Vertex packets | pvr_prim() calls |
| --- | ---: | ---: | ---: |
| 40 model triangles | 40 | 120 | 160 |
| **Nominal total** | **40** | **120** | **160** |

At 32 bytes per packet, the source-derived nominal packet shape is 5,120
bytes per frame. This excludes list/scene control, PVR buffer reservation,
tile/object-pointer overhead, CPU transform time, and any additional work
introduced by clipping. It is not a frame-rate or hardware-throughput claim.
Clipped triangles can produce more output triangles, so scenes near a buffer
limit need headroom.

The model's 1,336-byte embedded source is read-only asset data. The loader
reserves arrays for at most 96 decoded vertices and 192 indices, and the
32x32 texture uses 2,048 bytes of PVR texture storage plus its CPU upload
staging array. There is no per-frame heap allocation in the example.

## Modeling guidance

For a first Dreamcast model, start with a small number of triangles, one
opaque list, one power-of-two ARGB4444 texture, UVs in 0..1, and a model
centered near the origin. Keep seams intentional: each seam may duplicate a
vertex in the converted data. Split very different materials into separate
meshes so their PVR polygon headers and list choices remain visible.

The satellite is intentionally only 40 triangles. It demonstrates the
pipeline without pretending to establish a maximum. Increase geometry in
small steps, inspect the generated counts, build a CDI, and then measure the
actual result on the intended Dreamcast video mode or Flycast configuration.
The emulator check is useful for loader and image regressions; it does not
replace a physical-console performance run.

## Validation boundary

The converter was checked on 2026-10-01 with Python 3 and produced the counts
above. The target ELF and Flycast run must still be performed in the pinned
KOS container; a successful host build does not establish that KOS headers,
the SH-4 ABI, PVR texture allocation, or runtime rendering are correct. No
physical Dreamcast run is claimed by this document.
